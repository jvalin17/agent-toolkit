# Architecture: Role-Based Agent System (v4 — Final)

> Generated by /architecture on 2026-08-16
> Based on: requirements/role-context-layer.md + user refinement + 62 repos researched
> Research: BMAD, 7 agentic repos, SWEBOK v4, Team Topologies, Accelerate, Brooks, FAANG + startup role taxonomies
> Revision: v4 — 19 roles finalized, role_init health checks, skill mapping, product scenarios validated

## Vision

Roles are **specialized agents with pre-learned domain knowledge** from indexed open-source repos. They follow deterministic skill workflows. The LLM is the executor — it writes code, reads files, runs commands — but the **orchestrator (skills + hooks) decides WHAT to do and WHEN**. Knowledge is invested upfront (LLM cost at index time) to save cost at runtime. Each role uses existing skills extensively and has pre-computed bug patterns with fixes ready.

## LAYER 0: Health Check System

### Per-Session (fast — runs every session)

Only `detect_role.py` runs at session start. It does file pattern matching — no API calls, no LLM, takes milliseconds.

```python
# In session_init.py, alongside existing startup

detected_roles = detect_roles(project_dir)  # file pattern matching only
role_context = load_role_preambles(detected_roles)  # read .md files
# Inject into build_context() — done
```

### Scheduled Health Check (NOT per-session)

Heavy checks run on a schedule or on-demand, never at session startup.

```python
# roles/role_init.py (NOT BUILT — use learn.py --health instead) — called by /updater or cron, NOT session_init

def check_all_roles_health() -> List[RoleHealthReport]:
    """Full health check for all roles. Run weekly/monthly or via /updater."""
    reports = []
    for role in load_all_roles():
        report = RoleHealthReport(role=role.name)

        # 1. Knowledge exists?
        synthesis = load_synthesis(role.name)
        if not synthesis:
            report.add_gap("NO_KNOWLEDGE", f"No _synthesis.md for {role.name}")
            reports.append(report)
            continue

        # 2. Knowledge fresh? (check file modification date)
        age_days = days_since_modified(synthesis.path)
        if age_days > 90:
            report.add_gap("STALE", f"Knowledge is {age_days} days old")

        # 3. Repos updated? (GitHub API — cached, rate-limited)
        for repo in load_repos_json(role.name):
            latest = check_repo_latest_release(repo)  # cached GitHub API
            if latest and latest > repo.get("indexed_version", ""):
                report.add_gap("REPO_UPDATED", f"{repo['name']} has new release: {latest}")

        # 4. Knowledge complete? (all required sections present)
        required = ["advisory", "anti_patterns", "quality_checks", "bug_fixes"]
        for section in required:
            if section not in synthesis.sections:
                report.add_gap("INCOMPLETE", f"Missing section: {section}")

        # 5. Cross-role consistency (no conflicting advice)
        conflicts = check_cross_role_conflicts(role.name, synthesis)
        for conflict in conflicts:
            report.add_gap("CONFLICT", conflict)

        reports.append(report)
    return reports
```

### When Each Check Runs

| Check | Trigger | Frequency | Cost |
|-------|---------|-----------|------|
| Role detection (detect_role.py) | Session start | Every session | Free (file matching) |
| Knowledge freshness | `/updater` or cron | Weekly/monthly | Free (file dates) |
| Repo version check | `/updater` or cron | Monthly | Low (GitHub API, cached) |
| Knowledge completeness | At index time | After synthesis | Free (section check) |
| Cross-role consistency | At index time | After synthesis | Free (text comparison) |
| Full re-index | Manual or scheduled | Quarterly | ~$2-3/role (LLM) |

### Gap Resolution Flow

```
/updater runs health check
  → finds stale knowledge for "backend" role
  → finds repo "nestjs/nest" has new major version
  → generates gap report

User reviews gap report
  → approves re-index for backend role

Research Engineer invoked (deterministic)
  → re-indexes nestjs/nest
  → re-synthesizes backend/_synthesis.md
  → validates completeness
  → done
```

## LAYER 1: Knowledge Acquisition Pipeline

### What Each Role Learns

| Category | What to Extract | Example (Backend) |
|----------|----------------|-------------------|
| **Project structure** | Directory layout, file naming, module organization | `src/routes/`, `src/models/`, `src/middleware/` |
| **Patterns** | Design patterns used, architectural decisions | Repository pattern, middleware chain, dependency injection |
| **Conventions** | Naming, error handling, logging, config management | `camelCase`, structured errors with codes, env-based config |
| **Anti-patterns** | What the repo explicitly avoids or has issues with | No raw SQL, no sync I/O in handlers, no global state |
| **Bug patterns + fixes** | Common bugs and their ready-made solutions | N+1 → eager loading; missing index → add index on FK; sync I/O → use async |
| **Dependencies** | What libraries are used and why | Express for routing, Prisma for ORM, Zod for validation |
| **Testing** | Test structure, what's tested, coverage approach | Co-located tests, integration > unit, test factories |
| **Performance** | How the repo handles scale, caching, optimization | Connection pooling, Redis caching, pagination patterns |
| **Security** | Auth patterns, input validation, secrets management | JWT + refresh tokens, Zod schemas at boundaries, env vars |

### What NOT to Learn

- Proprietary/paid service integrations (keep to open-source)
- Repo-specific business logic (extract patterns, not domain)
- Outdated patterns from old commits (latest main only)
- Opinions without evidence (only learn from production-quality repos)
- Monetary/payment system internals (learn the pattern, not the vendor)

### Knowledge Acquisition Process

```
Step 1: CURATE — select repos per role (human + LLM)
  Input: role definition (expertise areas)
  Process: search GitHub for top repos by stars, activity, quality
  Output: roles/{role}/repos.json — curated list with rationale
  Human: reviews and approves repo list

Step 2: INDEX — analyze each repo (Python + LLM)
  Input: repo URL from repos.json
  Process:
    a. Clone/fetch repo (Python — no LLM)
    b. Parse structure: file tree, package.json/deps, configs (Python — no LLM)
    c. Extract key files: entry points, routes, models, tests (Python heuristics)
    d. Send extracted code to LLM with structured prompt:
       "Extract patterns, conventions, anti-patterns, and bug fix patterns
        from this code. Output as structured markdown with categories."
    e. Store result in roles/{role}/knowledge/{repo-name}.md
  LLM cost: ~10K tokens per repo (input) + ~2K tokens (output)
  Total per role: ~5 repos × 12K = ~60K tokens (one-time, ~$1-3)

Step 3: SYNTHESIZE — merge repo learnings into role knowledge (LLM)
  Input: all knowledge/{repo-name}.md files for the role
  Process: LLM merges, deduplicates, resolves conflicts, ranks by frequency
  Output: roles/{role}/knowledge/_synthesis.md — unified role knowledge
  LLM cost: ~20K tokens (one-time per role)

Step 4: VALIDATE — human reviews synthesized knowledge
  Input: _synthesis.md
  Process: human reviews, adjusts, approves
  Output: approved _synthesis.md becomes the role's runtime knowledge base

Step 5: REFRESH — scheduled re-index (monthly/quarterly, NOT per-session)
  Input: repos.json + existing knowledge
  Trigger: /updater skill or cron job
  Process: re-run Step 2-3, diff against existing, flag changes
  Output: updated knowledge with changelog
```

### File Structure


## LAYER 2: Role Execution

### LLM vs Deterministic — The Boundary

| Component | Who Decides | LLM Involvement |
|-----------|-------------|-----------------|
| **Which roles are active** | `detect_role.py` (deterministic) | None — file pattern matching |
| **Role health status** | `role_init.py` (scheduled) | None — file dates + API checks |
| **Which skill workflow to follow** | `route_to_skill.py` (deterministic) | None — regex intent matching |
| **Which skills each role uses** | `role.md` config (deterministic) | None — defined in role file |
| **What knowledge to load** | Skill workflow (deterministic) | None — load `_synthesis.md` |
| **When to invoke other roles** | Skill workflow steps (deterministic) | None — `invokes:` field in role.md |
| **What code to write** | LLM | Full — but guided by pre-learned knowledge |
| **What bugs to fix** | LLM, using pre-computed bug patterns | Guided — pattern→fix pairs from `_synthesis.md` |
| **How to evaluate output** | LLM, using role criteria | Guided — quality checks are the criteria |
| **Whether to escalate** | Manager guardrail (deterministic) | Minimal |

### Role Definition Format (role.md)

```markdown
---
name: backend
scope: API development, server-side logic, data pipelines, service wiring
not_scope: UI rendering, native mobile, infrastructure provisioning
detect:
  files: ["server.*", "app.*", "src/routes/**", "src/controllers/**"]
  deps: ["express", "fastapi", "django", "spring-boot", "nestjs", "hono"]

  - Build API skeletons (routes, controllers, models, middleware)
  - Set up database connections and ORM configuration

  - Set up error handling and logging
skills:
  primary: ["/implementation", "/debug_tool"]
  secondary: ["/architecture", "/setup", "/precommit"]
  evaluation: ["/reviewer", "/evaluate"]

  after_skeleton: ["dba", "security"]
  after_pipeline: ["data-engineer"]
  after_deployment: ["infrastructure"]
  for_evaluation: ["security", "qa", "production"]

  cheap: ["file-search", "lint", "format", "boilerplate-generation"]

```

### Multi-Agent Execution (for complex tasks)

For complex functionality, the orchestrator spawns multiple cheap agents in parallel:

```
Complex task: "Build a stats API with dashboard"

Orchestrator (deterministic):
│
├─ Spawn cheap agents in parallel:
│   ├─ Agent 1 (haiku): Backend scaffolds API routes + models
│   ├─ Agent 2 (haiku): Frontend scaffolds dashboard components
│   ├─ Agent 3 (haiku): DBA designs schema + indexes
│   └─ Agent 4 (haiku): QA writes test stubs
│
├─ Expensive agent (opus): Reviews all outputs, resolves integration
│
├─ Cross-role evaluation (cheap agents):
│   ├─ Security reviews (haiku)
│   ├─ Production Engineer verifies (haiku)
│   └─ Code Health checks (haiku)
│
└─ Output: integrated, evaluated code
```

### Cross-Role Invocation Flow

```
User: "Build a stats API for player performance"

Orchestrator (skill workflow, deterministic):
│
├─ 1. detect_role.py: backend (primary), dba (secondary), frontend (if UI)
│
├─ 2. Load knowledge: backend/_synthesis.md, dba/_synthesis.md
│
├─ 3. Backend role EXECUTES using /implementation skill:
│     → Reads learned patterns from _synthesis.md
│     → Has bug patterns + fixes ready (e.g., N+1 → eager loading)
│     → Builds API skeleton: routes, controllers, models
│     → Writes tests (TDD from /implementation)
│
├─ 4. Skill workflow: "after_skeleton → invoke dba, security" (deterministic)
│
├─ 5. DBA role EVALUATES using /evaluate skill:
│     → "N+1 risk → add eager loading" (fix ready from knowledge)
│     → "Missing index on player_id → CREATE INDEX" (fix ready)
│     → "Use cursor pagination, not OFFSET" (fix ready)
│
├─ 6. Security role EVALUATES using /reviewer skill:
│     → "Missing rate limiting → add express-rate-limit" (fix ready)
│     → "No input validation → add Zod schema" (fix ready)
│
├─ 7. Backend role APPLIES fixes (not findings — actual code fixes)
│
├─ 8. Production Engineer VERIFIES using /verify skill:
│     → Runs the API, hits endpoints, checks responses
│     → Measures response times
│
├─ 9. Manager guardrail CHECK (deterministic):
│     → All quality checks pass? Scope maintained? Risks addressed?
│
└─ 10. Output: production-quality stats API
```

## LAYER 3: Cross-Role Evaluation

### Evaluation Protocol

Roles provide **fixes, not just findings**. Each finding includes a ready-made solution from pre-learned knowledge:

```markdown
## Evaluation Output Format

### Role: dba
### Evaluating: stats API
### Against: dba/_synthesis.md

#### Findings:
| # | Severity | Finding | Fix (ready) | Source |
|---|----------|---------|-------------|--------|
| 1 | HIGH | N+1 query in getStats | `include: { player: true }` in Prisma query | prisma-examples.md |
| 2 | HIGH | Missing index on player_id | `CREATE INDEX idx_stats_player ON stats(player_id)` | drizzle-orm.md |
| 3 | MEDIUM | OFFSET pagination | Switch to cursor: `where: { id: { gt: cursor } }` | nestjs-starter.md |

#### Verdict: NEEDS_CHANGES (2 HIGH findings with fixes ready)
```

### Verdict Rules (deterministic)

- 0 HIGH + 0 MEDIUM = **APPROVED**
- Any HIGH or ≥2 MEDIUM = **NEEDS_CHANGES**
- All checks pass + 0 findings = **APPROVED_CLEAN**

## Manager Guardrail

```markdown
# roles/manager.md — injected alongside active roles (~200 tokens)

5 principles:
1. QUALITY — check anti-patterns before implementing
2. SCOPE — solve exactly what was asked
3. DEPENDENCIES — check all applicable roles' guidance
4. RISK — address flagged risks, don't defer
5. ESCALATION — follow user instructions when role guidance conflicts
```
