# Requirements: Role Context Layer

> Generated by /requirements on 2026-08-16
> Mode: feature
> Scope: skill enhancement / infrastructure
> Project state: existing (agent-toolkit)

## Problem Statement

AI coding agents make domain-ignorant decisions — e.g., computing stats on page load instead of lazy-loading, writing N+1 queries, storing secrets in code. Today, users manually add instructions to CLAUDE.md per project. There's no systematic way to inject domain expertise into skill workflows, and no intelligence about when to use cheap vs expensive agents for different tasks.

## Core Requirement

A **role context layer** that auto-detects or manually assigns domain roles (frontend, backend, DBA, etc.), injects role-specific advisory context into existing skills, and includes a **role manager** that coordinates between roles and determines agent cost routing — all without blocking or overriding explicit user instructions.

## Boundaries

- **Advisory only** — roles inject context, never block actions
- **Does not override** explicit user instructions (user says "compute on load" → role doesn't fight it)
- **Works out of the box** — auto-detection from codebase, no mandatory config
- **Roles don't overstep** — each stays in its lane, role manager prevents conflicts
- **LLM-agnostic** — must work with any AI coding tool, not Claude-specific

## User Stories

- As a developer, I want the agent to automatically know my project is a React frontend so it avoids performance anti-patterns like heavy computation on page load.
- As a developer working on a full-stack app, I want multiple roles (frontend + backend + DBA) to advise simultaneously without contradicting each other.
- As a developer, I want to override the auto-detected role when the agent gets it wrong (e.g., it detects Node.js backend but it's actually a CLI tool).
- As a developer, I want cheap agents used for mechanical tasks (linting, file search) and expensive agents reserved for architecture/security decisions, without manual configuration.

### F2: Auto-Detection

| Capability | Input | Output | Source | Priority |
|-----------|-------|--------|--------|----------|
| Detect roles from codebase | File patterns, dependency files, project structure | List of applicable roles (ranked) | Design | must |
| Multi-role detection | Full-stack projects with multiple concerns | Ordered list: primary + secondary roles | Design | must |
| Detection caching | First scan result | Cached in `.session/` state (hook-managed) | Design | should |
| Confidence scoring | Detection signals found | High/medium/low confidence per role | Design | should |

**Detection runs in `session_init.py`** — scans project root for signal files, determines applicable roles, injects into session context.

### F3: Manual Override

| Capability | Input | Output | Source | Priority |
|-----------|-------|--------|--------|----------|
| Config override | `"roles": ["frontend", "dba"]` in `gates.json` | Overrides auto-detection | User request | must |
| Env var override | `AGENT_TOOLKIT_ROLES=frontend,dba` | Same as config | Existing pattern | must |
| Additive mode | `"roles_add": ["security"]` | Add to auto-detected roles | Design | could |
| Exclusion mode | `"roles_exclude": ["devops"]` | Remove from auto-detected | Design | could |

### F4: Role Manager

| Capability | Input | Output | Source | Priority |
|-----------|-------|--------|--------|----------|
| Coordinate active roles | List of detected/configured roles | Merged context without conflicts | User request | must |
| Resolve conflicts | Competing advice from two roles | Priority-based resolution | Design | must |
| Scope enforcement | Role attempting to advise outside its domain | Suppress out-of-scope advice | User request | must |
| Skill integration | Active skill + active roles | Role context injected per skill phase | Design | must |

**Conflict resolution priority:** User instructions > explicit role config > role manager defaults > auto-detected roles.

**Role manager is NOT a separate agent** — it's logic in the hooks that determines which role contexts to include and how to merge them. Think of it as the "conductor" that assembles the advisory context before injecting it.

### F5: Agent Cost Orchestration

| Capability | Input | Output | Source | Priority |
|-----------|-------|--------|--------|----------|
| Task tier classification | Task description + role context | cheap / mid / expensive | Research | must |
| Model routing guidance | Task tier | Recommended model (haiku/sonnet/opus) | Research | must |
| Fan-out vs single-agent | Task decomposition | Parallel cheap agents vs single expensive | Research | should |
| Progressive escalation | Cheap agent struggling (high iterations, failures) | Escalate to next tier | Research (SWE-Router) | could |

**Cost tiers (industry consensus):**

| Tier | Model | Tasks | Key signal |
|------|-------|-------|-----------|
| Cheap | haiku | File search, linting, formatting, boilerplate, simple refactors | Bounded scope, mechanical, read-only |
| Mid | sonnet | Code generation, bug fixes, test writing, standard review | Creative but well-scoped |
| Expensive | opus | Architecture, security audits, complex debugging, planning | Bad answer costs more than model cost |

**Integration:** Cost orchestration is defined per-role. Each role specifies which of its tasks are cheap-agent-safe vs need expensive agents. The role manager aggregates these into a unified routing table that existing skills consult when spawning sub-agents.

### F6: Injection Points

| Capability | Input | Output | Source | Priority |
|-----------|-------|--------|--------|----------|
| Session-level injection | `session_init.py:build_context()` | Role preamble in session context | Codebase analysis | must |
| Per-prompt injection | `route_to_skill.py` | Role-specific context alongside skill routing | Codebase analysis | must |
| Per-skill sub-files | Skill SKILL.md references | Role-aware sub-skill selection | Codebase analysis | should |

**Injection architecture:**

```
session_init.py → detects roles → injects role preamble
                                  ↓
route_to_skill.py → matches skill → appends role context for that skill
                                    ↓
SKILL.md execution → role context visible to agent → advisory influence
```

## Assumptions

- Assumed: Role definitions are markdown files (like skills) because the existing toolkit uses markdown for all instruction files
- Assumed: Auto-detection is fast enough to run at session start (<1s) because it only checks for file existence, not file contents
- Assumed: Multiple roles can be active simultaneously because real projects span multiple domains
- Assumed: Role context is small enough (~500 tokens per role) to not bloat the context window, keeping total injection under 2K tokens for 3-4 active roles

## Dependencies

- `session_init.py` — role detection + session-level injection
- `route_to_skill.py` — per-prompt role context injection
- `gates.json` — role configuration fields
- `install.sh` — symlink `roles/` directory to `~/.claude/roles/`

## Reusable from Codebase

- `get_config_value()` in `gate_hook.py` — already supports env var overrides, reuse for `AGENT_TOOLKIT_ROLES`
- `SKILL_CONTEXTS` pattern in `route_to_skill.py` — same injection mechanism for role contexts
- `build_context()` in `session_init.py` — add role preamble alongside existing config summary
- Agent frontmatter `model` field — already supports per-agent model selection for cost routing
